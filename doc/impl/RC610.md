# RC610 line printer

## Maintained scope

Every maintained monitor includes printer, kind 14, device 7, interrupt 10.
Compatibility, protected and DFC403 monitors are built from monsrc/sim4000.mops;
hjmops* remain historical references. MIPS/TS uses the compatibility monitor.
All shipped configs define RC610 with automatic, profile-specific append output.
CMake links the C implementation in ordinary builds; tests remain opt-in.
Binary packaging includes the printer-capable compatibility/protected monitors,
configs and native backend. DFC403 remains an additional source-tree profile,
not an extra binary-archive disk profile.

The User Manual's line-printer chapter owns operating instructions. This file
owns implementation policy and bounded evidence. There is no maintained
printer-free build option. Shipped disks and historical sources are unchanged.

## Hardware evidence and contract

RCSL 55-D54, RC 4000 Peripheral Devices: RC 610 Line Printer Reference Manual,
Tom Sandvang, September 1969 (archive 30007708), specifies the hardware.
Printed pages 2--5 were checked visually, including the graphic-code table,
rather than relying only on OCR. The multiprogramming-system description,
section 13.9, specifies kind 14, reservation and guest messages.

monsrc/montxt4 h10 implements the seven-bit transfers, line controls, sense
and interrupt waits. montxt3 dispatches kind 14; montxt9 p18/s18 generates the
descriptor and write address. mon8s g90 reserves printer, formats a memory
range, sends output and releases it. That command does not print a disk file.

| Operation | Native interpretation |
| --- | --- |
| Sense (0) | Return status in RC bits 0--5; reading never clears it. Busy during printing. |
| Control (1) | No effect, including while busy or offline. Not a reset. |
| Read (2) | No effect; no fabricated data or input interrupt. |
| Write (3) | Consume the low seven register bits, ignoring higher bits. Busy during printing. |
| Modifiers | All 16 modifiers ignored. |

The monitor unpacks three characters per guest word; the device consumes only
one character per hardware Write. Graphics fill 132 positions; overflow is
lost and counted. Standard Shift-In accepts codes 32--125 except 35, 36, 64,
94 and 96: 88 glyphs plus space. National codes 91--93 and 123--125 stay raw
seven-bit bytes, not Unicode. Unsupported graphics and optional HT/SO/SI/CAN/ESC
controls are ignored and counted.

| Print control | Host byte | Interpretation |
| --- | --- | --- |
| NL (10) | LF | Next line. |
| VT (11) | VT | Preserve format-track-1 motion, without a physical tape model. |
| FF (12) | FF | Preserve form/page motion, without a physical tape model. |
| CR (13) | CR | Same-line return/overprinting; never append an invented LF. |

Each control prints the buffered line, clears it and completes with one
interrupt. Ordinary graphics produce no completion interrupt. The model uses
one positive advance per print and no graphic-transfer delay, not the real
12-microsecond transfer / up-to-100-millisecond mechanical timing. Local mode
can fill the buffer but delays print start until remote selection. Local
selection during printing is deferred; paper loss after start permits the
current line to finish. Physical feed overlap and format tapes are not modeled.

RC bit numbers are MSB-first in a 24-bit word; CPU busy/disconnected flags
are separate from status.

| RC bit | Mask | Clearing rule |
| --- | --- | --- |
| 0 | 0x800000 | Intervention; next Write clears it. |
| 1 | 0x400000 | Parity/printing error; next Write clears it. |
| 2 | 0x200000 | Timer/mechanical fault; explicit master clear only. |
| 3--4 | 0 | Unused. |
| 5 | 0x040000 | Paper/drum condition; correct the physical condition. |

Hardware faults, local/remote selection and paper correction have separate
C APIs, not invented guest Control operations. Interrupt polling acknowledges
pending interrupts, not status. The file backend additionally exposes a
latched output error as virtual offline/paper-out, never fabricated parity.

## Host files and lifecycle

rc610_open exclusively creates a new regular output. rc610_open_append creates
or appends a regular file with O_APPEND, never truncating. Both reject symlinks,
FIFOs and device files; new files use mode 0600 and close-on-exec. FILE paths in
configs are configuration-relative. CLI attach paths are working-directory
relative. APPEND is accepted only for RC610 and requires FILE.

Defaults are printer.txt, printer.protected.txt, printer.mipsts.txt and
printer.dfc403.txt, each with APPEND=YES. The default/compat alias intentionally
shares the same profile. Concurrent emulator instances need separate working
directories; append is not a cross-emulator job scheduler.

A print-operation stream is emitted, not rendered paper. Each print writes its
graphics and original control, then calls fflush before the completion interrupt.
This also happens for CR/VT/FF and after a short write's accepted prefix.
A separate reader sees output before close; guest-side buffering may still
delay delivery to the device. There is no per-line fsync or crash-durability
claim. Short writes and flush/close failures are reported, not replayed.

Close refuses an active print. It discards/counts an incomplete unprinted line,
never emits it retroactively. CPU reset preserves device/file state. Normal
frontend shutdown advances an already accepted hardware print, then closes
and reports output errors. Paper correction or timer clear does not hide an
output failure. A successful new output connection clears that backend error,
not unrelated hardware latches. No guest job boundary or per-job file splitting
is inferred.

CLI attach/detach and show media expose file selection and counters. Bare
attach requires a new file; attach DEVICE FILE append preserves existing text.
Runtime output is automatic with the shipped configs, not dependent on attach.

## Generated monitors and provenance

Before this work the compatibility monitor had no printer descriptor and
device 7 / IRQ 10 were unused. Devices 5/6 already belonged to terminals;
the historical printer-on-5 example was therefore unsuitable.

The maintained option is:

```text
t.18 i.10 d.7 n.printer             ; RC610 line printer
```

For DFC403, the guarded --dfc403 preparation selects the existing t.8 hardware
disk option instead of the t.7 accelerated disk entries in a disposable copy
of the same generation file. Reader/punch remain IRQ 9/12, matching every
current config. --protected selects sim4000-protected.mops: its guest editor
removes the recognized e22 key-setting bypass in temporary ptxt10, then calls
the shared build at FP input depth 2 and restores the guest original afterward.
Python only validates inputs/results, never patches the Protection source.
No additional driver/supervisor source patch is needed for the printer.
Combined protected/DFC403 is not an accepted profile.

## Bounded acceptance and limitations

- Native tests cover seven-bit input, all modifiers, independent graphic/status/
  interrupt values, no-op commands, 132-column overflow, raw controls, local/
  paper transitions, errors, no replay, exclusive/append file policies and
  visibility from a second reader before close.
- Guest-s print of IRQ-0 vector address 16 completes twice with both
  compatibility and protected monitors and with the DFC403 monitor; a later
  system command remains usable. These are transport checks, not independent
  validation of every numeric field or explicit reservation-owner inspection.
- Protected mode requires actual task instructions in nonzero-key memory.
  A mismatched compatibility monitor with protection enabled fails before date
  initialization instead of silently falling back to unprotected mode.
- Compatibility/DFC403 boot and text/binary transfers pass. Protected transfers
  use the matching UNIT0.protected profile and its rcin/rcout/system binding.
  Testing the original newer fromhost/tohost under protection is not a valid
  substitute; their known incompatibility remains.
- A guest Algol source-listing program opens cpuregtest as an area (mode 4)
  and printer as a physical device (mode 0). It prints 630 operations and
  17,309 bytes, beginning with MPROFILE and ending with the source's final end.
  No source execution or numerical regression run is involved.
- The same source-listing program also passes with MONITOR.protected and
  UNIT0.protected, importing via rcin and independently exporting via rcout.
  Both variants require exactly 630 prints/17309 bytes, a normal FP end,
  whole-file equality before close, no printer errors, finis and a later s list.
  The protected run observes 3547317 keyed task instructions during ptext itself
  with protection enabled. No source/library/media modification is needed.
  Wrapper hashes protect the monitor, base disk, fixture and tutorial example;
  fixture/example identity is required. All disk writes use volatile COW.
- FP o printer and printer=copy cpuregtest did not drive the hardware in
  exploratory sessions; do not document them as file-print recipes. The
  accepted Algol example is shipped as examples/print_source.alg.
- MIPS/TS autostart with the existing disk pair supports actual PRIMO signup
  on printer/kind 14. The shipped primo_print.alg example submits a disk area
  through transfer actions 2 and 6. Two short and two 161-line jobs complete
  with result/reply 0, state 5, cause -1 over two emulator boots. All 15,144
  output bytes match independent input text, are visible before shutdown and
  survive restart append unchanged. The console contains completion records,
  not the payload. Signoff removes the displayed assignment. TEM/SOS password
  rejection, login, FP commands and logout still pass after each printing run.
  No startup-script, disk or PRIMO-generation change is needed. This does not
  establish unrestricted queue/resource reclamation or general error recovery.
- A transport submitted with the output detached reports printer end document,
  remains displayed with pin and waiting, and does not report completion or
  change the output file. TEM/PRIMO/SOS remain healthy while waiting. Reattach
  to the same file with append and PRIMO start printer complete it with result/
  reply 0, state 5/cause -1 and exactly one copy of the payload. Earlier output
  and subsequent jobs survive shutdown/restart. This is a pre-job disconnected
  endpoint test, not partial-write, disk-full or mid-job physical-paper recovery.
- The separate protected MIPS/TS assessment now passes two sequential local
  FP-to-PRIMO-to-RC610 jobs. Installed Algol compiles the unchanged example;
  rcin supplies source/payload without newer host-transfer-library dependencies.
  Both completions have result/reply 0, state 5/cause -1; 4538 bytes are exact
  and visible before shutdown. Signup/signoff and subsequent protected Telnet
  login/commands/logout pass. This is private diagnostic coverage, not a shipped
  protected MIPS/TS profile or remote SOS-client printing/restart acceptance.
- A separate bounded check defines two outstanding transports from independent
  150000-halfword new processes, each with temp disc 200/10 and perm disc 0/0.
  Distinct sender areas, printer descriptors and program names avoid shared-base
  catalog collisions. Both positive transport IDs coexist while output is
  detached. One client blocks in action 6; the second receives reply 3 (missing
  resources) for that action and falls back explicitly to bounded action-4
  queries. After reattachment/start both return reply 0, state 5/cause -1, and
  exact FIFO payloads appear once. The second idle client is removed and a new
  first-client transport completes on the same PRIMO instance. Full output,
  subsystem health and TEM login/logout survive the second boot. The installed
  generation text specifies waitops=1; the resource diagnosis below checks a
  larger runtime buffer claim without changing the binary. Arbitrary waiter counts and exhaustive
  resource reclamation remain unverified.

## PRIMO wait-resource diagnosis

Guest exports of startprimo and primotrim identify runtime buf 10/area 7 and
generation options prcount=3, oprcount=4, waittrans=300 and waitops=1. These last
two limits are different: queued transports versus pending blocking waits.
The generation option date 941109 matches the installed PRIMO startup banner.
The PRIMO reference (RCSL 31-D688, archive 30008479), printed page 63, defines
waitops as pending wait-and-get-state operations. Appendix D, printed page 75,
gives buffer consumption as 2 plus operator/device coroutine counts plus
waitops: 2+4+3+1=10 here. Source text is evidence, not an independently decoded
binary option table.

A guarded diagnostic removes only the unused private live PRIMO process and
recreates it from the same bprimo, first with buf 10 and separately with buf 11.
No guest start file, trimming input or program is edited. With eleven buffers,
PRIMO recommends buf 10 during startup; the second blocking wait still receives
reply 3. Exact queued output, the polling fallback, subsequent transport and
two-boot TEM/SOS checks pass. Merely increasing the runtime buffer claim is
therefore not a solution. Together with waitops=1 this strongly supports a
generated-PRIMO waiter limit, rather than a missing RC610/CPU configuration.
The exact binary refusal branch has not been independently identified.

Current main-catalog inspection finds bprimo and primotrim but not tprimo,
trcmol, rcmol, ttransfer or tfileutil. Higher blocking-wait capacity would need
an independently reproducible PRIMO regeneration, not just editing primotrim
or a host configuration. Do not patch the binary or enlarge the shipped claims
to conceal this limit. Sequential printing needs none of these changes.

The agreed printer implementation and acceptance block is complete (100% of
the current scope). Documentation source is current; the PDF is refreshed only
on request. Full reservation/numeric-format checks, partial host-write recovery,
mid-job paper recovery and queue exhaustion are deferred extensions, not active
completion requirements. This is not a claim of complete hardware fidelity.
PDF refresh remains explicit and is not a side effect of code/document changes.
